Code tour · plain language

How the code works

A walk through the DyTrustRec codebase, folder by folder — what each part does and why it exists, without the maths. Read it once and you can explain the project to anyone.

The whole thing in one sentence

We take Amazon reviews, clean them, turn them into a network of users and products, teach a model to walk that network, and have it recommend things — while explaining why and admitting how sure it is.

That's it. Everything in the code serves one of those six steps. If you understand the journey below, you understand the project.

The eight stops

Each stop is a folder. For each one: what it does, where it lives, and the single thing worth remembering.

1

Getting the data in

src/data/loader.py · validator.py

Downloads the Amazon file, reads it line by line (so it never loads 2.5 GB into memory at once), and translates it. Amazon calls a product parent_asin; the rest of our code calls it item_id. That translation lives in a config file, so swapping datasets means editing YAML, not Python.

Remember: if a field doesn't exist in the data, we say so — we never make one up. That's why there's no "seller" anywhere in the project.
2

Cleaning it

src/data/cleaner.py

Throws away rows that make no sense (a rating of 7 out of 5, a review dated 2031) and removes exact duplicates. Then it flags the suspicious ones — someone posting the same text on six products, or six reviews twenty seconds apart — and keeps them.

Remember: we flag suspicious rows but never delete them. The fraud detector later can't find what cleaning already threw away.
3

Splitting by time

src/data/splitter.py

Older reviews become the training set, newer ones the test set. Never random — a random split would let the model learn from a 2023 purchase and then get tested on a 2019 one, which is cheating.

Remember: train on the past, test on the future. It's harsh — 42% of test users were never seen in training — but it's honest.
4

Turning things into numbers

src/features/

Computers can't read "this controller broke in a week". sbert.py uses a small language model to turn each review into 384 numbers that capture its meaning — reviews about similar things end up with similar numbers. sentiment.py adds a positive/negative score. review_features.py adds six plain facts: how long it was, was it verified, how old is it.

Remember: 384 meaning-numbers + 6 fact-numbers = 390 numbers describing every review.
5

Building the network

src/graph/builder.py

This is the heart of it. Instead of a spreadsheet, the data becomes a web: users connect to products they bought, to reviews they wrote; products connect to their brand and category. Five kinds of thing, connected five ways.

Why bother? Because a web lets you find "people like you" through paths — you bought this, they bought this too, they also bought that. A spreadsheet can't do that naturally.

Remember: every connection is added in both directions, otherwise information could flow from users to products but never back.
6

Scoring trust

src/anomaly/cola.py · trust.py

CoLA looks at the network and asks "does this user behave like their neighbours?" Users who look odd get a high anomaly score. We flip that into a trust score between 0 and 1, and use it to make suspicious connections count for less.

Remember: this is the part that didn't work. See the last section — it's the most interesting thing you can say about the project.
7

Learning to recommend

src/models/hgt.py

HGT is the recommender. It repeatedly passes information along the network's connections, so each user's "fingerprint" gradually absorbs information about the products they touched, the brands behind them, and what similar users did.

After training, every user and product is 128 numbers. To recommend, we multiply a user's numbers by every product's numbers — a bigger result means a better match — and take the top 10.

Remember: we also built four simpler models in src/models/ to compare against. Without them the HGT numbers would mean nothing.
8

Explaining and showing

src/explainability/ · src/recommendation/ · app/

For each recommendation we search the network for actual evidence — shared category, shared brand, similar trusted users — and write a sentence from what we find. If there's no evidence, we say so instead of inventing a reason.

confidence.py adds how sure we are (a brand-new user gets low confidence even when the score is high), counterfactual.py answers "why not this other product", and the Streamlit app puts it on screen.

Remember: explanations are built from retrieved facts, never generated text. No evidence, no sentence.

The supporting cast

Four folders that don't transform data but hold everything together.

FolderWhat it's for
configs/Five YAML files holding every setting. No number is hard-coded in Python — change an experiment by editing YAML.
src/utils/Config loading, logging, random seeds, choosing CPU vs GPU. Boring but everything depends on it.
src/evaluation/The scorecard. Precision, recall, NDCG, coverage — the same code scores every model, so comparisons are fair.
tests/229 automated checks. They caught six real bugs.
scripts/Six commands you actually run — one per stage of the journey.

Running it, in order

Each script picks up where the last left off.

python scripts/prepare_data.py --tier dev   # stops 1–2  download & clean
python scripts/run_eda.py                   #           charts & statistics
python scripts/build_graph.py               # stops 3–5  split, features, network
python scripts/run_experiments.py           # stop  7    train & compare models
python scripts/run_synthetic_anomaly.py     # stop  6    test the trust scoring
python scripts/export_model.py              #           save results for the app
streamlit run app/streamlit_app.py          # stop  8    the dashboard

Add --tier smoke to the first command to run the whole pipeline on a small dataset in about 90 seconds — useful for checking nothing is broken before committing to the big one.

Jargon decoder

Six words that sound harder than they are.

WordPlain meaning
EmbeddingA list of numbers that stands in for something. Similar things get similar lists.
Heterogeneous graphA network with different kinds of node — users, products, brands — not just one kind.
SBERTA small language model that converts a sentence into 384 numbers capturing its meaning.
HGTThe recommender. Passes information along network connections so each node learns about its surroundings.
NDCG@10A score out of 1 for how good your top-10 list is, giving more credit for correct items near the top.
AblationRemoving one piece at a time to see which pieces were actually helping.
k-coreDropping users and products with too few interactions, so there's enough data to learn from.
LeakageAccidentally letting the model see the answers. The whole reason we split by date.

How to talk about the results

The honest version is also the more impressive one. Don't hide it.

What worked

Adding review meaning (SBERT) made recommendations 15% better. And the graph models recommend across 22–31% of the catalogue where the simple model only ever suggests 7% — so they're much better at helping people discover things.

What didn't

Two of our own ideas made things worse: the learned "fusion layer" (−22%) and weighting the training by trust (−19%). And no version of our model beat plain old matrix factorisation, the simplest baseline.

The interesting failure

We built fake review campaigns to test the trust scoring. It scored 0.295 where 0.5 is random guessing — meaning it thought the fake accounts were more trustworthy than real ones.

Why? CoLA flags users who don't fit their surroundings. But a coordinated fake campaign is highly consistent — same wording, same rating, same targets — so its members fit each other perfectly. To this detector, an organised bot network looks more normal than an unusual real person.

A one-line rule — "what fraction of this user's reviews are copy-pasted?" — scored 0.99 on the same test.

Say it like this

"The pipeline works and is fully tested. What failed was a hypothesis — that a graph anomaly detector gives a useful trust signal. We measured it properly, we can explain exactly why it failed, and that explains our other negative result too. Reporting it as a success wouldn't have survived scrutiny."
